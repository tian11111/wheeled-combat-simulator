# MuJoCo 双物理后端工程验证

## Goal

在 Windows x64 上为赛事模拟器增加可选的 MuJoCo 三维接触物理模式，以三维刚体/车轮/铲子/能量块接触替代该模式下的简化二维接触。用户应能在 Godot 桌面端观察、在 CLI 无画面批量运行，并通过可复现的工程测试判断它是否值得继续标定。现有物理模式仍为默认；旧场景、控制器和回放不因本任务改变。

## Confirmed Baseline and Decisions

- `docs/ARCHITECTURE.md:17-37`：CLI 与 Godot 共用 `MatchEngine`；当前二维物理、裁判和回放是单一权威，三维权威物理必须显式分模式/版本。
- `src/Sim.Core/MatchEngine.cs:47-50,112-116,592-600,623-707`：引擎和 FSM 直接依赖 `PhysicsWorld`；物理步进后按方块接触归属及台面位置判分。
- `src/Sim.Protocol/RobotAction.cs:8-16`：控制器发出的是米/秒与弧度/秒的 `v/w` 速度请求，不是电机力矩。
- `src/Sim.Cli/BatchCommand.cs:9-33`：无 Godot 的 batch 是 AI agent 入口，支持有界并行；`fidelity.json:27-56` 显示摩擦、碰撞、堵转未真机标定，登台仍为手绘模型。
- 用户已选择：首轮交付**双模式工程验证**、**不包含真机遥测标定**、**正式验收平台仅 Windows x64**。

## Requirements

### R1. 模式与旧行为隔离

- 场景显式选择 `mujoco` 才启用新后端；未填写物理模式的旧场景继续使用当前物理，不能默默切换。
- 旧模式的规则、事件顺序、快照 JSON、回放和 batch 稳定指纹保持原基线；新模式的行为/回放不冒充旧模式。
- 不改变现有控制器 `v/w`、传感器字段和裁判计分规则的含义。

### R2. 最小可用三维物理

- MuJoCo 模型包含官方场地的地面、6 cm 台面/台沿与围栏、两辆带底盘/车轮/铲子的差速车，以及两增益一减益共三块 15 cm 立方体。
- 场地平移/旋转、车体尺寸/质量、出生点和块位来自现有 `Scenario`/`FieldTransform`；显示用 glTF 不成为碰撞几何或物理输入。
- `v/w` 请求经有界车轮驱动进入动力学，车辆与方块的位置、三维姿态、速度和接触归属来自 MuJoCo；禁止直接瞬移车体来伪造轮地运动或登台。
- 保持裁判帧固定步长；MuJoCo 可在一帧内做固定数量子步。真实重启必须同步原生状态，且不改变罚分/计时/其他实体语义。

### R3. 同一权威跨端消费

- CLI `match`、`batch`、录制/检查回放与 Godot 实况/回放使用同一新后端，Godot 不另写物理或判分。
- 快照加性携带必要三维姿态；Godot 在新模式显示方块落下/翻转及车体俯仰/侧倾，旧快照继续按原方式显示。
- 首轮传感器仍消费现有解析模型和物理状态的平面投影；将与 MuJoCo 碰撞几何不一致的风险列入验证报告，不宣称传感器也已三维化。

### R4. 可复现、并行与失败边界

- 新回放标识物理模式、MuJoCo 原生版本与生成模型的内容哈希；版本/模型不匹配时明确拒绝复现。旧回放缺字段时按旧模式解释。
- 每场拥有独立的 MuJoCo 可变状态和明确的资源释放路径；同机同版本同输入的结果不应随 batch 并行度变化。
- 缺失/错误版本原生库、未知物理模式、无效新模式场景在执行前给出明确错误；batch 保持现有预检零 JSONL/运行期逐 seed 失败的退出语义。
- Windows x64 发布产物包含受版本与哈希锁定的官方原生库及许可声明，不要求用户手工把 DLL 放到系统目录。

### R5. 保真度诚实性

- 提供旧/新模式对照与新模式的性能、稳定性、规则事件报告；只声明工程验证，不将 `fidelity.json` 的未标定项晋升。
- 若某接触/登台场景未达标，报告具体输入、观察结果与模型缺口，并保持对应验收项未完成；不用硬编码运动结果、放宽回放检查或改旧基线掩盖问题。

## Out of Scope

- 改 MuJoCo 为默认、删除旧物理、重写裁判/控制器协议、重做 UI 或整个传感器模型。
- 采集真机遥测、拟合真实摩擦/电机/碰撞参数或将模拟结果称为真机成绩；这些留给既有真机遥测任务。
- Linux/macOS 原生库打包和跨平台逐位一致保证；跨平台支持另立任务。

## Acceptance Criteria

- [ ] AC1/R1：旧场景、旧回放、现有规则测试及 batch 固定指纹仍通过，旧序列化不新增 MuJoCo 字段。
- [ ] AC2/R2：至少有直行/转向、车车碰撞、推块出界、台阶登台与掉台的可重复场景；新模式无非有限状态、明显穿透或“位置跳跃式登台”，并输出对照记录。
- [ ] AC3/R2-R3：同一新模式场景在 CLI 与 Godot 的最终比分、结束原因、事件指纹一致；真实重启仍只回位目标车、对方 +3 且不延长时钟。
- [ ] AC4/R3：Godot 实际渲染能量块高度/朝向与车体三维姿态；旧快照和布局编辑仍可加载。
- [ ] AC5/R4：新回放能同机同版本复现，改变模型哈希/原生版本被拒绝；batch `--parallelism 1` 与 `4` 的逐 seed 稳定结果一致，完成 32 worker 资源/失败隔离压力检查。
- [ ] AC6/R4：Windows x64 干净环境能随应用加载已锁定原生库；缺库/坏场景预检清晰失败，不产生伪成功输出。
- [ ] AC7/R5：报告给出新旧模式的吞吐、实时倍率、峰值内存和场景差异；`fidelity.json` 未标定等级保持不变。
