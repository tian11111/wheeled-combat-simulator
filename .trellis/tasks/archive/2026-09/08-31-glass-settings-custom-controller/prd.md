# 玻璃控制台、运行设置与自定义小车控制器

## Goal

把 Godot 桌面端从当前的深色不透明赛事 HUD 升级为清晰、克制的玻璃质感控制台；提供可直接操作的运行设置入口；让用户能配置并启动自定义小车控制器，同时保持 `Sim.Core`、回放、布局编辑和无头批量仿真的权威边界不变。

## Confirmed Evidence

- 当前 HUD 由 `godot/src/HudPanel.cs:10-58` 程序化创建，包含状态卡、事件卡、操作帮助、回放条和布局编辑栏；其卡片颜色在 `HudPanel.cs:12-20` 是高不透明度深色，当前没有设置面板。
- 当前主场景只挂载一个 `CanvasLayer/HudPanel`，见 `godot/scenes/Main.tscn`；窗口以 1280×720 为设计视口，并用 `canvas_items` + `expand` + `fractional` 处理拉伸，见 `godot/project.godot:19-27`。
- `Main` 负责会话组装、命令路由和场景重建，`MatchSession` 重建 `MatchEngine`；布局编辑器只在比赛准备阶段编辑草稿并通过新的 `Scenario` 应用，不能把设置 UI 变成运行中修改引擎状态的后门。
- `Scenario` 是可复现比赛的完整输入，包含 `Field`、`Vehicles`、`Blocks` 和可选 `Parameters`；`Sim.Core.SimParameters.FromDictionary` 只接受现有命名参数。任何仿真参数设置必须在新会话/新比赛边界应用，不能修改正在运行的 `MatchEngine`。
- 外部控制器已经由 `src/Sim.Cli/PythonBridge.cs` 实现为独立进程 JSONL stdio 桥；协议、超时、request-id 校验、zero-action 回退和 fault 计数见 `docs/CONTROLLER_PROTOCOL.md`。CLI 已支持 `--controller-us`/`--controller-them`，但 Godot 桌面端尚未提供配置入口。
- 项目规范要求 Godot 只消费快照并路由裁判指令，Sim.Core 不依赖 Godot/IO/进程；渲染装饰不进入 `Scenario`、`Snapshot` 或回放指纹。
- 既有未提交改动 `.trellis/spec/frontend/component-guidelines.md`、`godot/README.md`、`godot/src/ArenaVisualizer.cs` 以及其他用户路径属于本工作区既有状态，本任务不得覆盖或混入无关回滚。

## Requirements

### R1. 玻璃质感赛事控制台

- 将实况、回放和布局编辑模式中的主要卡片统一为半透明玻璃风格：适度透明、圆角、细边框、层级阴影/高光和清晰的文本对比；不能继续呈现大块纯黑遮挡画面。
- 玻璃效果只改变 Godot 表现层，不改变 `RenderFrame`、事件文本、比分、快捷键、按钮回调顺序、布局编辑权限或相机输入所有权。
- 在 1280×720、当前窗口尺寸和 1920×1080 下保持关键文本可读，动态文本不能导致卡片重叠；全屏时 UI 与 3D 画面按同一套设计视口规则缩放。
- 玻璃卡片不得依赖第三方 UI 包、联网资源或外部运行时；若真实背景模糊在兼容渲染器不可用，必须有稳定的半透明颜色回退。

### R2. 设置界面与安全应用边界

- 从主控制台进入独立设置界面，并能返回比赛；设置界面至少覆盖窗口/显示配置（分辨率、窗口化/全屏、UI 缩放或等价可读性选项）以及用户确认后的仿真/控制器配置入口。
- 对所有可编辑数值显示单位、合法范围和无效输入提示；保存配置时不得写入官方场景、回放或 `fidelity.json`。
- 显示设置可以按 Godot 窗口能力即时应用；影响比赛可复现性的仿真参数必须标明“下场比赛生效”，在新 `Scenario`/新 `MatchSession` 创建时一次性应用，比赛进行中不得静默改变。
- 设置持久化必须是渲染/桌面偏好或用户独立配置文件，加载失败时回退默认值并给出可诊断提示；旧版本没有配置文件时能正常启动。

### R3. 自定义小车代码

- 用户能够为我方和/或对手配置自定义控制器，并在发令前看到当前角色的控制器来源、命令/脚本路径、连接状态和错误状态。
- MVP 优先复用既有独立进程 JSONL 协议和 `PythonBridge` 语义；自定义控制器不能直接引用或修改 Godot/Sim.Core 内存，不能绕过 request-id、超时、有限值校验或 zero-action/fault 处理。
- 每场比赛的控制器生命周期独立于其他场次；启动失败、超时、坏行、死进程必须安全回退并在 UI/日志中定位到角色，不得卡死桌面端或改变无头 batch 的既有生命周期契约。
- 自定义控制器配置只影响启动参数/外部控制器选择，不把控制器命令、机器路径或 UI 偏好写进 `Scenario`、回放指纹或核心结果。

### R4. 集成与回归

- 设置界面、玻璃 HUD 和控制器入口共享明确的桌面壳状态边界；关闭设置后原比赛/回放/布局编辑状态保持一致。
- 不修改 `Sim.Core` 规则、物理、传感器、计分、回放协议、官方布局常量或无头批量输出 schema。
- 增加可自动验证的设置校验/持久化、控制器错误路径和 UI 状态转换测试；真实 renderer 截图验证玻璃风格、全屏缩放和设置界面可读性。

## Acceptance Criteria

- [ ] 实况、回放、布局编辑三种模式均显示统一玻璃卡片；背景不再是大块高不透明度纯黑，关键文本、比分、事件和按钮仍清晰可读。
- [ ] 1280×720、1920×1080 和全屏窗口下 UI 锚点/字体/卡片比例随设计视口一致变化，无关键内容遮挡、重叠或不可操作控件。
- [ ] 用户可从主界面打开设置、修改受支持的显示项并返回；无效值被拒绝并显示原因，重启应用后持久化设置按约定恢复，配置文件损坏时安全回退。
- [ ] 用户可为至少一方配置外部控制器并在发令前看到配置状态；新比赛按配置启动控制器，成功动作生效，启动失败/超时/坏响应按既有 fault 与零动作语义处理且 UI 不冻结。
- [ ] 比赛进行中修改仿真参数不会改变当前引擎；应用到下一场后新 `Scenario` 使用参数，旧回放、旧 parity 和无头 batch 结果逐位不变。
- [ ] `dotnet test`、Godot parity、`--camera-smoke`、`--edit-smoke`、相关设置/控制器专项测试和真实 renderer capture 全部通过；`git diff --check` 通过。

## Recommended MVP Boundary

- 自定义小车代码推荐实现为“选择外部脚本/命令 + 角色绑定 + 启动前预检”，不在 Godot 内嵌完整 IDE，也不在进程内动态编译/执行任意 C# 或 GDScript。这样复用已有协议并保留进程隔离；代价是用户需要在外部编辑器维护代码。
- 仿真参数推荐先暴露已有 `SimParameters` 中有明确单位且适合场景覆盖的项目，并把高风险/实验性参数隐藏在高级区；不把所有内部常量直接变成无约束滑块。
- 本任务不引入数据库、在线控制器市场、远程执行、常驻 daemon、第三方 UI 主题包或新的真实机器人资产。

## Key Decisions

- 已确认：自定义小车代码采用“外部 Python/C# 等命令/脚本选择与角色绑定，复用现有 JSONL stdio 协议”；本任务不做 Godot 内嵌代码编辑器、进程内动态编译或任意代码执行沙箱。
- 已确认：显示/窗口设置即时应用；仿真参数和控制器配置只在新比赛或显式重置后应用，不修改正在运行的 `MatchEngine` 或当前回放。
- 已确认：首轮将现有 `SimParameters` 的全部已登记键做成白名单面板，分为“常用/高级”，每项提供单位、默认值、范围和实验性提示；不把未登记的内部常量暴露给用户。
