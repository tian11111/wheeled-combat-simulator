# Godot 3D 二轮视觉校正与相机拖拽方向修复

## Goal

基于 2026-08-29 实机截图和用户反馈，对已经完成第一轮的 Godot 3D 赛事画面做一次小范围、可验证的收敛：修正左键拖动视角上下左右均反向的问题，按官方规则图纸校正擂台表面“外侧四角纯黑、中心纯白”的渐变，消除对角亮带，并继续改善机器人/擂台的空间层次。保持 HUD、仿真权威、回放、无头 batch 和既有 glTF 外观接口不变。

## Evidence and diagnosis

- 当前相机的左键旋转实现位于 `godot/src/MatchCamera.cs:352-373`：横向使用 `_yaw += screenDelta.X * YawPerPx`，纵向使用 `_pitch -= screenDelta.Y * PitchPerPx`；用户实机反馈四个方向均与预期相反，因此本任务要反转这两组符号和俯视自旋符号，而不是重写输入所有权或右键平移。
- `godot/src/Main.cs:307-326` 的 `--camera-smoke` 目前验证的是旧方向契约；修复后必须同步更新冒烟期望值，并增加四方向断言，避免文档/测试把反向行为重新固定回来。
- 当前传感器灰度模型位于 `src/Sim.Core/FieldModel.cs:80-88`：`t = max(|dx|, |dy|)`，再由 `godot/src/FieldGrayTextureMap.cs:60-61,70-100` 直接映射进 128×128 台面纹理。这个 L∞ 方形范数会让同一欧氏半径上的对角方向更亮，并把边中点也压到黑色，因而产生截图中明显的白色对角亮带；这不是物理、传感器噪声或规则事件。
- 规则图纸 `D:/project/robocup/1779761830740288.pdf` 第 10 页的文字明确写“擂台表面底色从外侧四角到中心分别为纯黑到纯白渐变”，图 1 展示的是平滑的中心径向/椭圆渐变，没有四条白色对角线。该图纸的尺寸文字是几何依据，效果图是显示外观依据。
- 当前 `godot/src/ArenaVisualizer.cs:136-149,218-239,544-557` 已有 Unshaded 台面路径，但它仍把核心灰度数值直接当作显示亮度；`Main.tscn` 还启用了 SSAO/反射探针等全局渲染层，必须用纯色/A-B capture 区分“渐变模型”与“renderer 三角面/后处理伪影”。
- 当前用户截图显示：第一轮取景和深色背景已可用，但台面中心过于像发亮贴图，机器人仍是简化图元，擂台边缘和物体接触感不足；本任务只做第二轮小步优化，不扩展为 UI 重构或资产引入。

## Requirements

### R1. 左键拖拽方向

- 将左键拖拽定义为可观察、可测试的“反向修正”契约：鼠标向右/向下产生的 `screenDelta` 应分别使概览/跟随环绕角与当前实现相反；俯视模式的水平自旋也反转。垂直拖动的俯仰限幅仍为 10°–85°。
- 保持左键只负责旋转、右键抓取平移、滚轮缩放、C 切换、F5 重置和 `PointerInputEnabled` 所有权；布局编辑器激活时相机仍完全让出指针。
- 旋转行为不能改变机器人位姿、比赛状态、场地变换或回放数据。

### R2. 官方擂台渐变

- 显示层采用独立的“中心到四角”渐变函数：归一化平台局部坐标后，用到中心的欧氏距离相对于角点距离进行归一化，中心为纯白、四角为纯黑，边中点为中间灰度；红色中心方区优先覆盖渐变，白“武”字保持独立视觉层。
- `src/Sim.Core/FieldModel.FieldGrayLocal` 的 0–1000 传感器语义保持不变，不将显示修正偷偷变成物理/传感器模型变更；视觉函数只消费场局部平台边界和中心，由 `Scenario`/`FieldTransform` 提供几何来源。
- 台面纹理继续走 Unshaded、无错误光照梯度的路径；用纯色 A/B 测试排查纹理过滤、两个三角面的接缝、深度冲突、SSAO 和反射探针影响。最终画面不得出现白色对角亮带、斜向接缝或红区边缘光晕。
- 新的纯函数测试必须覆盖中心、四角、四个边中点、等欧氏半径的轴向/对角向样本、红区覆盖和坐标轴方向；不能只测试“对称点同值”而漏掉对角亮度偏差。

### R3. 第二轮空间层次收敛

- 在不引入第三方资产的前提下，针对截图中最明显的层次问题微调现有程序化材质、光照、平台边缘、机器人 fallback 分件、接触阴影和能量块可读性；禁止大规模重做 HUD 或场景架构。
- 取景应保留完整擂台、围栏、出发区和机器人安全边距，且不让 HUD 卡片遮住关键比赛区域；只调整 3D framing/灯光时不得改变 HUD 节点层级、锚点、文本、按钮和快捷键。
- 所有装饰仍是 render-only，尺寸由现有 `Scenario.Field`/机器人视觉尺寸推导，不得新增碰撞体、规则几何、随机数或状态判断。
- 保留现有 glTF 外观导入、法线修复、坏模型 fallback 和团队/登台指示接口；本任务不新增 GLB、纹理、HDRI、字体或音频。

### R4. 兼容性与真实性边界

- 不修改 `Sim.Core` 物理、碰撞、摩擦、堵转、登台、计分、传感器采样、协议、回放 schema、`fidelity.json` 或 AI agent 无头 batch 行为。
- 视觉层不得根据灰度贴图反推或写回仿真状态；传感器值、旧回放和跨端事件指纹必须保持逐位一致。
- 不以 dummy/headless renderer 的“启动成功”代替画面验收；视觉声明必须有真实 Forward+ renderer 截图和运动镜头检查。

### R5. 证据与性能

- 在 1280×720 和 1920×1080 下分别保留修复前/修复后真实 renderer capture，至少包含默认概览、俯视、左键拖动后的机位和运行中机器人/能量块。
- 记录灰度纯函数输出、截图像素分桶、相机 smoke、编辑器 smoke、parity 和测试结果；临时 PNG、性能日志、`.import` 文件不进入提交。
- 如果 SSAO、反射、抗锯齿或其他后处理相对同机同场景基线造成约 30% 以上帧时间退化，或产生运动拖影/灰度污染，则默认关闭该项并记录可复现的实验配置。

## Out of Scope

- 不改变核心 `FieldGrayLocal` 传感器模型来“顺便”修图；不把官方效果图误当成未经标定的真实传感器空间地图。
- 不引入第三方机器人模型、纹理、HDRI 或新的运行时依赖；真实资产升级另开任务并做来源/许可证/尺度/法线审计。
- 不重做深色赛事 HUD，不修改按钮布局、事件栏、回放条、快捷键或编辑器工作流。
- 不引入 SDFGI/VoxelGI/Lightmap 烘焙、复杂全屏 shader、物理材质或新的场地真值。

## Acceptance Criteria

- [ ] Overview、Follow、Top 的左键拖动四方向符合新的反向契约；Top 仍保持固定俯视角，右键平移/滚轮缩放/编辑器指针所有权不回归。
- [ ] `--camera-smoke` 更新后通过，并对横向、纵向正负拖动分别作断言；`--edit-smoke` 通过。
- [ ] 显示渐变的中心为白、四角为黑、边中点不被错误压成黑色；等欧氏半径轴向/对角向亮度一致，红区和白“武”字正确。
- [ ] 1280×720/1920×1080 真实截图与官方规则图纸的外观关系一致：无四条白色对角亮带、无明显三角面接缝、无后处理造成的灰度假梯度；擂台主体、机器人和能量块层次比当前截图更清楚。
- [ ] 灰度传感器数值、`Scenario`/`Snapshot`/回放、Sim.Core 行为、旧 parity 指纹和无头 batch 均无非渲染变化。
- [ ] glTF 可选入口、缺法线修复、坏模型 fallback、团队识别和登台指示回归通过；本任务没有新增第三方资产。
- [ ] HUD 布局与文字可读，3D 后处理没有污染 CanvasLayer；双分辨率性能对照完成，高成本选项按门限正确关闭或记录。
- [ ] `dotnet test`、官方回放 `replay-check`、Godot parity、camera-smoke、edit-smoke 和真实 renderer capture 验收证据齐全。

## Key Decisions

- 相机采用“反转当前旋转符号”的最小修复，保留既有输入所有权和右键抓取语义，不重写相机状态机。
- 台面显示采用独立的官方外观渐变函数；核心 `FieldGrayLocal` 继续作为传感器模型，避免为了显示效果改变仿真和旧回放。
- 第一轮不引入第三方资产；继续保留 `RobotModelLoader` 的 glTF 接口作为下一阶段真实模型升级入口。
- 先修正渐变模型并用纯色 A/B 排除 renderer 伪影，再做有限的材质/灯光/构图微调；重型 GI 和全屏特效不进默认方案。

## Deferred Items

- 若后续需要达到真实转播级机器人外观，另开任务引入经过许可证审计的 GLB/纹理/HDRI，并复用本任务保留的 glTF 接口。
- 若有新的官方高分辨率贴纸/灰度资产，应单独建立版本化视觉参考与像素误差门禁；本任务使用规则 PDF 图 1 作为外观基准，不把 PDF 图片直接打包进运行时。
